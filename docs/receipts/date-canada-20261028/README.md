# Canadian date presentation: artifact-only policy proposal

At clean product HEAD `1fda25bdec72d5beabd34fbe7e15abe807489f00`, the documented October 26 locale policy intentionally uses day/month/year for non-CJK locales other than the stated English exceptions; neutral `en` intentionally keeps ISO. It does not bundle CLDR data. In the bounded Linux fixture, both `en-CA` and `fr-CA` displayed ISO value 2027-03-04 as `04/03/2027` and presented picker columns day → month → year. Pinned Chromium 156.0.8078.47 `Intl.DateTimeFormat` reported `2027-03-04` and year → month → day for both tags. That Intl result is a locale reference, not proof of the browser's OS-native date-input UI.

The recorded `canada.patch.gz` decompresses to the patch (SHA-256 `43d61a02ae85c41877cf36507388a56fb963709fbc55e648c92d579dc3f2fbeb`) deliberately expands the current policy for `en-CA` and `fr-CA` to year-month-day with hyphens and reorders the shared date picker accordingly. It retains the previous strict day/month/year slash parser as a legacy alias: for example `03/04/2027` continues to mean April 3, rather than being reinterpreted. ISO input remains accepted. The patch does not claim comprehensive CLDR or Intl parity.

Paired native Linux X11/AT-SPI fixtures verified both Canadian displays and picker column order. Programmatic `TextInput::set_text` followed by the public `DateField::commit_text` exercised legacy and ISO input, ambiguous slash dates, invalid April 31 and non-leap February 29, rejection of year-first slash input, default 1900–2100 range rejection, and DateTime legacy/ISO values with 05:06 preserved. Neutral `en`, `en-US`, `en-GB`, `zh-CN` and `de` controls retained their previous display, entry outcomes and picker order. `evaluate.py` passed; `result.json` SHA-256 is `f22e71372a03f2456a1ad70ecb2cc99effe369b27221d90e77dfa9c116aa115c`. The two native binaries SHA-256 are `606c8d66bf61324ba4bb9974dc273aafe10106e4c4df1a0b7a3b7446ec10a69d` (baseline) and `2531d03da46729dd5241b1261df3e58a750e93f4fc33f9f0fef62b78d8dd2ec6` (candidate).

Source snapshots were identical before and after both builds and captures: baseline manifest SHA-256 `359e8556a20e77707a9db69f6a6f611df9772c0b7d7e7b19c24011e785bcbfa3`; candidate manifest `b015ef5a3f739a7a13f665f07938b34db3d419ee783e5f8e8d121779bc0b8b2c`. Candidate snapshot verifies its copied product differs only in `date_field.rs` and exactly matches the patch. Builds used the shared Codewhale lock; `git apply --check` and `rustfmt --check` passed. The earlier pre-pair baseline evidence is retained in the local artifact directory `date-canada-probe/pre-candidate-baseline/`.

Compatibility review: Canadian slash parsing follows the old order, separator and width validation, and ISO still takes the existing direct parse path; committed values remain ISO, range validation remains unchanged, and an in-progress draft continues to use its saved presentation. The legacy slash alias is intentionally ambiguous to readers unfamiliar with the old policy, so the field should display its canonical hyphen form after a successful commit. The fixture does not exercise actual physical keyboard/IME entry, locale changes mid-draft, reader speech, macOS, Windows runtime, or every locale and date value. No canonical source was edited.
