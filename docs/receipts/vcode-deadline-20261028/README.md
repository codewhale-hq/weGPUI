# Verification-code countdown elapsed-time probe

The public `VcodeButton::set_seconds` contract says the button is idle after the configured number of seconds. The existing implementation decrements once per completed timer, so a stalled process can extend the countdown. This is weGPUI's resend behavior; the pinned WeUI example has no countdown.

At clean HEAD `d52145dbe728f032abf21a06991ca390f192a551`, paired isolated Linux X11 applications used a three-second countdown and live AT-SPI. Only the fixture process was paused. The baseline was stopped for 4.537 monotonic seconds and, after resuming, still exposed disabled `Resend (2s)` with one Send event. The candidate was stopped for 4.557 seconds and, after its next scheduled update, exposed enabled `Send code` with one Send event. Both variants passed reset, restart, cancel-then-wait, natural expiration and callback-count checks; three deliberate starts produced exactly three Send events. `result.json` contains the captured labels, states and timings. A previous experiment using `std::time::Instant` is preserved under `instant-experiment/`; it was replaced because it would bypass GPUI fake clocks.

The recorded `vcode.patch.gz` decompresses to a patch with SHA-256 `62729a88739bdae1200d89388a0310f5c1995fe89f675a4ef3f090e5e6186f2c` uses `background_executor().now()` for both the initial timestamp and elapsed time, preserving the scheduler clock abstraction. GPUI's test scheduler uses a controllable `TestClock`; production uses the platform dispatcher's clock. This compatibility was source-inspected, not executed under a fake scheduler. The code computes `seconds - floor(elapsed_seconds)`, equivalent to a ceiling of the remaining duration for an integer-second countdown. Elapsed seconds are capped before conversion to `u32`; the chosen seconds are captured at start, so later configuration changes affect later starts. `reset` still drops the owned task, and GPUI's `Task` contract says dropping cancels it; the live cancel/restart control observed no late event or state change.

The patch catches up on its next one-second scheduled tick, not necessarily exactly at the deadline while execution is blocked. Monotonic clock behavior across actual machine sleep is platform-dependent and was not tested. This is not a macOS, Windows, sleep/wake, screen-reader speech, or full component parity result.

Source snapshots before/after build and runtime match (SHA-256 `6059557dff80fb8af73faa1ec9972b4e7f8084774ddf9296044991f9cdebc3bc`); paired native binary SHA-256 are `fdbab9dfbb8fa2fcb0bce233b1582dc8d21ced441f189658c5f4ec397cfa3a9c` (baseline) and `db86b67f86dca814dae76a4a4d4957be2ff0a7689d91154376b94d2695ccdeeb` (candidate). `evaluate.py` passed; `git apply --check` and `rustfmt --check` passed. Builds used the shared Codewhale build lock. No canonical source was edited for this probe.

The final product source is identified in `product-source.json`. The macOS ARM64 library suite passed 54 tests and strict all-target Clippy. The Windows x64 GNU all-target cross-check passed with the [recorded wrapper](../windows-cross-20261028/README.md); it did not execute Windows tests. Five website inventory tests and selected root/project-prefix browser checks passed.
